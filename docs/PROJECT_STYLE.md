# Project Style Guide

Derived from the patterns actually used in the codebase. Follow these when extending the project instead of inventing new patterns.

**Product name**: the app is **Verdant Bank** (renamed 2026-08-22 from the generic working title "Banking Management System" — see [DECISIONS.md](DECISIONS.md)). The GitHub repo slug/URL (`banking-management`) is unchanged; only the product name changed.

## UI Style
*(Rewritten 2026-08-22 — a full visual/UX redesign replaced everything below. The pre-redesign version of this section described a plain, no-design-system look with a `#1a1a2e`/`#2d5be3` navy-and-blue palette, system fonts only, a single `.page-loading` text block for loading states, and one `768px` breakpoint. None of that is accurate anymore — this is the current state.)*
- **Visual direction**: a real design-token system, still hand-written CSS in `client/src/index.css` (no Tailwind/MUI/component-library dependency — that constraint held through the redesign, it just got much more structured). Tokens: color scale, type scale, spacing scale, radius scale, shadow scale, motion/easing — all CSS custom properties under `:root`.
- **Color**: deep emerald/green as the primary brand color (`--brand-*` scale, `--brand-600` for primary buttons/links), a charcoal-navy "ink" scale for dark surfaces (`--ink-*`, used for the header brand mark, the account "bank cards," and the auth screen's dark panel), a cool neutral gray scale for text/borders/surfaces (`--gray-*`), and semantic tokens for success/danger/warning/info (each with a `-50`/`-100` tint and a `-600`/`-700` text-safe shade). Status badges use `Badge` component tones (`success`/`warning`/`danger`/`info`/`neutral`), not the old `.badge-active`/`.badge-pending`/`.badge-closed` classes.
- **Typography**: Inter (loaded via Google Fonts `<link>` in `client/index.html`, weights 400–800), with a defined type scale (`--text-xs` through `--text-4xl`) and `font-variant-numeric: tabular-nums` on all monetary/numeric figures (balances, amounts, table numeric columns) so digits align.
- **Spacing/radius**: a numbered spacing scale (`--space-1` through `--space-16`, 4px-based) and a radius scale (`--radius-sm` 8px / `--radius-md` 10px / `--radius-lg` 16px / `--radius-xl` 22px / `--radius-full` for pills) — use the tokens, don't hardcode new pixel values.
- **Shadows**: a layered shadow scale (`--shadow-xs` through `--shadow-lg`, plus a dedicated `--shadow-dark` for dark surfaces like the account cards) instead of one reused recipe.
- **Buttons**: shared `Button` component (`client/src/components/ui/Button.jsx`) with `variant` (`primary`/`secondary`/`ghost`/`danger`), optional `size="sm"`, and a `loading` prop that shows an inline spinner and disables the button — don't hand-roll a new button style, use this component (or its underlying `.btn`/`.btn-*` classes if a plain `<button>`/`<Link>` styled as a button is genuinely needed, e.g. `NotFound.jsx`'s "Go home" link).
- **Icons**: a small hand-rolled `Icon` component (`client/src/components/ui/Icon.jsx`) with a fixed named set of simple line icons (no external icon-library dependency) — check the existing name list before adding a new one; add new icons there rather than inlining raw SVGs elsewhere.
- **Forms**: label + input pairs wrapped in `.field` (label gets `.form-label` or matches via the `.field > label` selector). Icon-prefixed inputs (email, password, search) use an `.input-group` wrapper with an `Icon` at `.input-icon`; the password field's show/hide toggle uses `.input-toggle`. Native `<select>` for enums, styled with a custom chevron background-image, no custom dropdown component.
- **Cards**: `.card` is still the generic container. `.account-card` is now a distinct dark "bank card" treatment (gradient ink background, masked account number with reveal + copy-to-clipboard). `.stat-card` gained an icon badge (`.stat-icon`). New: `.card-header` (title + optional action row) and `.card-icon-title` (icon + heading pairing).
- **Navigation**: single sticky top `AppHeader` (in `Navbar.jsx`) with role-aware `NavLink` items, a user-menu dropdown (avatar/initials, name, role, Logout), and a slide-down mobile drawer below the `860px` breakpoint. Still no sidebar, no breadcrumbs.
- **Tables**: plain HTML `<table>`, wrapped in `.table-wrap`. Rows use hover highlighting; numeric/monetary columns use `.cell-muted` (secondary) or `.amount-credit`/`.amount-debit` (colored) as appropriate. Combined name+email cells use `.cell-user-text`. No virtualization (fine at current data volumes).
- **Tabs**: a new segmented-control pattern (`.tabs`/`.tab`/`.tab.active`) used for the Deposit/Transfer switcher on the customer dashboard — reuse this for any future "pick one of a few short-lived views" UI rather than inventing a new tab style.
- **Modals**: still none. If one is needed, establish the pattern deliberately.
- **Notifications**: still inline `.error-text`/`.success-text` paragraphs per form, now with a leading `Icon` (`alertCircle`/`checkCircle`) as a sibling of the message text — **never wrap the message text itself in an additional child element**, since several components' tests use React Testing Library's exact-text `getByText`, which fails with a "multiple elements" error if both a wrapper and its only child independently match the same string. Still no app-wide toast system (tracked in [TECHNICAL_DEBT.md](TECHNICAL_DEBT.md)).
- **Loading states**: `Skeleton` primitives (`client/src/components/ui/Skeleton.jsx` — `SkeletonLine`, `SkeletonCards`, `SkeletonStats`, `SkeletonRows`) replace the old single `.page-loading` text block on dashboard pages. `ProtectedRoute`'s auth-resolving loader still uses plain text ("Loading...") — kept deliberately simple since it's a brief, one-line gate, not a data-heavy page.
- **Empty states**: shared `EmptyState` component (icon + title + description + optional action button) — use this instead of a bare line of text for "nothing here yet" states going forward.
- **Error states**: same `.error-text` convention as form errors; table empty-state rows use `.table-empty`.
- **Responsive behavior**: several breakpoints now, not one — `900px` (auth split-screen collapses to single column), `860px` (header nav collapses to the mobile drawer), `640px` (page padding tightens, stat grid drops to 2 columns, header user-menu name hides), `420px` (stat grid drops to 1 column). `.account-grid`/`.stat-grid` still use `auto-fill`/`auto-fit` grid so they reflow without needing every breakpoint spelled out.
- **Accessibility**: paired `<label htmlFor>`/`id` on every field (unchanged). Added: a global `:focus-visible` outline (brand-colored), `prefers-reduced-motion` handling (disables/shortens transitions and the skeleton shimmer animation), `aria-label`s on icon-only buttons (account-card reveal/copy, password show/hide, mobile menu toggle). Still not verified: full color-contrast audit, `aria-live` on dynamic error/success text, keyboard navigation of the table pagination controls.
- **Animations/transitions**: now used deliberately and consistently — a shared `--ease-out`/`--dur-fast`/`--dur-base`/`--dur-slow` set of motion tokens, applied to hover/focus states, the user-menu dropdown's entrance, button press feedback, and skeleton shimmer. Keep new motion within this token set rather than inventing new durations/easings.

## UX Style
- **Interaction patterns**: dashboards fetch their own data on mount (`useEffect` + `useCallback`) and re-fetch after a mutation (e.g., opening an account or completing a transfer immediately reloads the relevant list) rather than optimistic local updates.
- **Navigation principles**: role determines landing route (`/dashboard`, `/employee`, `/admin`) computed in `App.jsx`'s `Home` component and `Navbar`'s `dashboardPath`. Keep these two in sync if adding a role or changing routes.
- **Feedback patterns**: every mutating action (open account, transfer, suspend user, etc.) shows a disabled-button "in progress" label (e.g. "Transferring...", "Opening...") rather than a separate spinner component.
- **Error handling UX**: API error messages are read from `err.response?.data?.message` and shown verbatim — the backend is expected to send human-readable `message` strings (it does, consistently, via `errorHandler` and controller-level `res.status(x).json({message: ...})`). Keep that contract when adding new endpoints.
- **Confirmation behavior**: none implemented yet (e.g., suspending a user or transferring funds has no "are you sure?" step). Worth adding for destructive/high-stakes actions (user suspension, account closure) before this is a real product.
- **Mobile behavior**: functional via the single breakpoint; not deeply optimized (tables scroll horizontally rather than reflowing to cards on mobile).

## Code Style
- **Naming conventions**: camelCase for variables/functions, PascalCase for React components and Mongoose models, kebab-case is not used anywhere (files are camelCase/PascalCase, not `kebab-case.js`).
- **File naming**: one component/controller/model per file, filename matches the exported name (`AccountCard.jsx` exports `AccountCard`, `accountController.js` exports the account controller functions).
- **Folder conventions**: backend follows `models/ → middleware/ → controllers/ → routes/` layering; frontend follows `components/` (reusable/presentational) vs. `pages/` (route-level, own data fetching) vs. `context/` (cross-cutting state) vs. `api/` (HTTP client setup).
- **Function conventions**: backend controller functions are plain `async function name(req, res) {}` (named, not arrow, not default-exported individually — grouped and exported as an object at the bottom of each controller file). Route files wrap every controller in `asyncHandler(...)` — **do not add a new route without this wrapper**, or thrown errors in that handler will crash the process instead of reaching `errorHandler`.
- **State management patterns**: local `useState`/`useEffect` per page; `AuthContext` is the only cross-cutting context. Don't reach for Redux/Zustand unless state genuinely needs to be shared across more than 2–3 components — it doesn't yet.
- **API patterns**: REST, one router file per resource (`authRoutes`, `accountRoutes`, `transactionRoutes`, `adminRoutes`), mounted under `/api/<resource>` in `server.js`. Validation via `express-validator` arrays declared inline in the route definition, checked by the shared `validate` middleware. Follow this shape for new resources rather than validating inside the controller.
- **Error handling**: controllers throw/reject and let `asyncHandler` + `errorHandler` deal with it; they don't try/catch internally except where a specific status code needs custom handling (e.g. insufficient balance → `400` with a specific message).
- **Validation**: `express-validator` at the route layer for auth and transfers; ad hoc manual checks in controllers for simpler cases (e.g. `accountController.js` checking `accountType`). If a new endpoint takes user input beyond a simple enum, prefer adding `express-validator` rules over manual `if` checks, to match the established pattern.
- **Comments**: none in the current codebase by design — code is written to be self-explanatory via naming. Keep it that way; only add a comment for a genuinely non-obvious constraint (e.g. the compensating-refund comment in `transactionController.js` explaining *why*, not *what*).
- **Logging**: `console.log`/`console.error` only, no framework. Server start and DB connection log on boot; errors log via `errorHandler`. Don't add `console.log` debugging statements that would ship to production — remove them before considering a change done.
- **Testing conventions**: none established yet — see [TESTING.md](TESTING.md) for the intended approach when tests are introduced.
